# Grill decisions — 19 Sep 2026

One line per decision, appended as each agenda branch is resolved. Format: `N.k — <decision>`. Source of truth for the PRD; overrides drafts in `styles/*.md` where they differ.

1.1 — Style resolution is code-only: each `styles/<name>.md` declares aliases in front matter; the resolver scores the style line by alias hits, highest wins, zero hits or tie → `explainer`; no LLM in the loop. The full free-text style line is passed to the planner as a "style note" usable only where the spec leaves latitude (length, caption language, energy). Resolved name + note are stored on the job and shown on the page before submit.
1.2 — Every `styles/<name>.md` = YAML front matter + the five prose sections. Front matter must carry seven key groups: `aliases`, `beats` (min/max/target mean/max consecutive same-mode), `presenter` (allowed modes, full-frame max fraction, PIP diameter+anchor, ring look), `broll` (allowed kinds, motion per kind, allowed enter transitions), `captions` (font, size, weight, words-per-page range, emphasis cap, anchor y, max lines), `sound` (bed dB under voice, band, duck max, allowed hit kinds + placement, forbidden list), `finale` (kind, length). A loader test validates all specs at startup; renderer and QA read only the numbers, the planner reads numbers + prose.
1.3 — User references refine exactly three things: (1) subject identity — a reference of the product/person/place is preferred B-roll for beats about it, outranking sourced assets; (2) palette — `animated` and `hitech` may take the accent colour from the references' dominant colour, `explainer`/`educational` keep fixed palettes; (3) one mood adjective added to the music query. All front-matter numbers are untouchable by references. Reference clips are stills in v1 (one extracted frame per beat that uses it, no playback). The planner receives references as a captioned one-line-each list, not as images, until a vision step exists.
1.4 — Specs carry `status: shipped | draft`. Only `explainer` is shipped on day 14; aliases of draft specs resolve to `explainer` with a visible page notice ("hitech not available yet, using explainer"). Day-14 rating is against `explainer` only. Before day 14, one draft style must render a smoke short end to end — not judged, only to prove the style system works beyond explainer. Drafts flip to shipped one at a time after one rated short each.
2.1 — Inputs validated server-side in the upload endpoint (page limits are hints only). Raw video: one mp4/mov ≤ `SHORTSMITH_MAX_UPLOAD_MB`, ffprobe must show one video + one audio stream, duration 20 s–8 min; reject if mean volume < −50 dBFS ("no speech found"). Any orientation accepted with a "vertical works best for PIP" warning, but the centre-crop to 1080x1920 must obey the 1.5x upscale rule: if filling 1080x1920 from the source needs > 1.5x upscale (landscape 1080p does), reject with "record vertical or in 4K" — soft crops are the research.md prototype failure. Written brief: required textarea, 40–1500 chars, placeholder shows topic / angle / must-say facts / hook wish. Style: one text field with shipped-style chips, live-resolved per 1.1. References: ≤ 8 files (jpg/png/webp/mp4/mov), ≤ 20 MB each, optional one-line caption each, images ≥ 600 px short side.
2.2 — One directory per job under `SHORTSMITH_DATA_DIR`: `jobs/<job_id>/{job.json, input/, work/, out/}`. `job.json` is the only index (no database in v1): inputs, resolved style + note, status, timestamps, cost ledger. `input/` holds raw.mp4 as uploaded, brief.md verbatim, `refs/<n>_<slug>.<ext>` + `refs.json` (caption, original name, dimensions, `rights: owner_supplied` — the first rows of the rights log). `work/` holds cut, asr, plan, assets, stems, frames. `out/` holds short.mp4, contact.jpg, credits.md, rights.json, meta.json. Retention: `input/` and `work/` deleted at 24 h; `job.json` and the whole `out/` live 7 days — rights evidence must outlive the upload.
2.3 — The planner receives one Pydantic `PlanRequest`, nothing from disk, no pixels: `brief` (verbatim), `style` (loaded spec: numbers + prose), `style_note`, `transcript` (list of `{text,start,end}` after ASR fixes + per-segment logprob flags), `references` (list of `{id, kind: image|clip_frame, caption, width, height}`), `constraints` (`max_duration_s`, `target_duration_s` from the style note if it names a length, else the spec default), `asset_policy`. Prompt sections in fixed order: spec numbers, spec prose, brief, style note, references, transcript — brief precedes transcript so brief = intent, transcript = material. Planner is instructed that brief facts also spoken in the transcript must land as a stamp/label/card; QA checks every reference id the brief marks "must use" appears in the plan.
3.1 — A beat = contiguous span of the cut voice track with one presenter mode, one visual kind, one asset, at most one landed event; beats tile the runtime with no gaps. Explainer front matter: `min_s: 0.7`, `max_s: 6.0`, `set_piece_max_s: 8.0` (list/chart/split/wall/finale), `target_mean_s: 2.5` validated as plan mean in 2.0–3.2 s (else one planner re-cut request). Planner proposes boundaries in seconds; code snaps each to the nearest transcript word end within 0.15 s ("no cut mid-word" by construction), clamps, and rejects the plan only if a snapped beat still violates min/max. Density check: max gap between consecutive visual events (beat starts + landed events) ≤ 1.5 s.
3.2 — Presenter modes: `full`, `pip`, `off` (`cutout` deferred past v1, needs a matte). The draft "never more than ~2 consecutive beats in the same mode" is dropped (references ran PIP x6 and were rated perfect). Explainer front matter: `full_max_fraction: 0.25` (hard), `full_never_consecutive: true`, `pip_max_run: 6`, `off_max_run: 3`. Every `full` beat must carry one reason tag from {cold_open, emotional_line, argument_turn}; validator rejects any other. Hook beat is `full` or `off` with hook cards, never `pip`. Finale is `off` (the finale card carries the presenter in its centre circle). All counts are style numbers so other styles change them without code.
3.3 — PIP face point is measured once per job by code: 8 stills at the research strip times, face detector (OpenCV Haar or mediapipe, whichever `uv add` allows), median face box; no face in ≥ 6 of 8 → job fails early with "we could not find your face, please record facing the camera". Crop window = full source width, square. Priority when head+collar exceeds the square: keep the chin, clip hair — window placed so the chin sits at 82 % of window height (`pip.chin_anchor: 0.82`). If face-box height > 45 % of source width, PIP circle grows 300 → 340 px (`pip.large_face_diameter`). Both are explainer front matter. Upload page shows one guideline line: "Sit about an arm and a half from the phone, face in the top third". The 8-frame PIP strip is written to `work/frames/` for the contact sheet; no job blocks on a human.
3.4 — Hook is two beats of fixed shape, planner fills the slots. Beat 1 cold open: `full`/`cold_open`, 0.7–2.0 s, punch-in per research §2; the cold-open span may be lifted from anywhere in the recording (the only editorial reordering in v1), and the planner must state `hook.original_position: keep | drop` for the lifted line at its original place — no accidental repeats; validator rejects a plan whose lifted span appears twice without an explicit `keep`. Beat 2 hook cards: `off`, 2.0–4.0 s, title ≤ 8 words in caption typography + three cards from plan assets in priority order (user references, then best sourced); < 3 assets at render → one centred card, never blank. Plan fields: `hook.title`, `hook.cold_open_span`, `hook.original_position`, `hook.card_asset_ids`. Code validates title word count and word-boundary span. The brief's hook wish is a hint; a title that ignores a numeric hook wish is a contact-sheet warning, not a rejection.
4.1 — B-roll kinds are tiered in explainer front matter; the planner may only use tier 1 until tier-2 components exist. Tier 1 (day 14): `photo` (full-bleed Ken Burns 1.10→1.16, alternate in/out and pan direction per consecutive beat), `card` (framed archival: white 14 px border, rotate −1.5°, blurred darkened cover, caption strip, push 1.45→2.1, optional red ring at a point), `stamp` (rotated text, lands in 0.16 s with shake, palette yellow/green/red, top 60 % only), `lower_third` (name + role, fade 0.35 s), `hook_cards` and `finale` set-pieces (mandatory), `presenter_full` and `presenter_pip` pseudo-kinds. AMENDED by 9.2: tier 1 also includes `list`, `chart`, `split`, `wall`, `map`, `infographic`, `pin_drop`, `route_arrow`, `label_flyin`, `counter`, `object_path`. Tier 2: full parallax depth and vector-illustration style only (animated skin); naming a tier-2 kind on a shipped style is a validation error naming the nearest tier-1 substitute, and the planner prompt lists the tiers. Every non-presenter beat has exactly one motion; a still with no motion is a validation error ("no static still ever").
4.2 — Planner labels every non-presenter beat with `subject_kind` + `query`. `entity` (named person/place/product/org/event): `card`/`photo` from owner refs → search → generate, plus `lower_third`; AI generation is allowed on entity beats only as the last fallback; generation serves what the script demands when reality has no image (e.g. "Lincoln as a boy") and never replaces a findable real image. Photoreal generation is allowed and encouraged for scenes, environments and unnamed people (a photoreal vintage street, a generic child evoking young Lincoln) — no forced illustration filter. The only ban: photoreal recreation of the specific named person or specific product presented as if it were a real photo of it; that depiction stays illustration-style matching the style's look (vintage, cartoon, painterly). `concept` (idea/feeling/process/generic scene): `photo` Ken Burns from generic search or AI, `stamp` for the key word. `number` (stat/price/date/count): `stamp` over the previous beat's asset with continued Ken Burns, or `card` if a reference shows the number; no new asset. `quote` (the line is the point): `presenter_full` with reason tag, or `stamp` of the phrase over the previous asset. The asset step refuses any source the label forbids. Generated assets carry `depicts: named_entity | scene` plus `render: photoreal | illustration` in the rights log; validator rule: `depicts: named_entity` requires `render: illustration`; `render: photoreal` on `depicts: scene` is normal and passes. At least one `entity` beat per 60 s unless the brief has no proper noun.
4.3 — Asset count is by unique assets, not beats. Explainer front matter: `unique_assets_min: 12` per 60 s (below reads as a slideshow), `unique_assets_max: 24` per 60 s, `reuse_max: 4` beats per asset. Reuse is encouraged: the planner is told callbacks/payoffs/number beats returning to an earlier asset is what the references did; validator warns if no asset is reused. `number` and `quote` beats add nothing to the count (4.2), so a typical 24-beat short needs ~16–18 fresh assets. Generated-image cap is set separately in branch 5.
4.4 — Fallback when nothing relevant is found is a fixed ladder applied by code in the asset step, never by the planner: (1) search with `query`, then once more with the planner-supplied `query_fallback` (broader term); (2) generate as illustration within the branch-5 cap; (3) reuse the nearest earlier asset with the same `subject_kind`, re-dressed — new crop or punch-in, continued Ken Burns, `stamp` of the beat's key word — never the identical framing twice, so the reuse reads as a deliberate callback; (4) mode swap to `presenter_pip` over a style-palette gradient with the stamp. Never a black or blank frame. Each beat records `asset.fallback_rung: 0..4`; the contact sheet marks rescued beats (rung ≥ 3); more than 4 rescued beats per 60 s fails the technical gate with "not enough relevant B-roll".
5.1 — OVERRIDE of the brief's "rights-safe by default, any-source operator-only" rule and the matching CLAUDE.md line (both to be rewritten in the PRD): web image search (Google Images style) is a primary source for every user in v1. Source order: owner references → web image search → Wikimedia Commons → Openverse → Pexels/Pixabay → generate (illustration, per 4.2). No licence filtering in v1 and no licence-filter logic is built; every asset logs its source URL (and page URL when followed) in the rights log. Web-sourced images are always re-dressed per the card/archival patterns (crop, frame/border, subtle effect), never shown raw. Planner emits `source_intent: search | generate | reuse` as a hint; code honours `reuse` always, `generate` only on concept beats, and always searches first on entity beats. A beat is never skipped (4.4 rungs 3–4). Each source is one adapter behind an `ImageSource` interface with a `Fake`; the order is a config list so a misbehaving source can be removed without code.
5.2 — `ASSET_POLICY` is repurposed as web-search on/off: `any` = full 5.1 order (default in `.env.example`), `rights_safe` = same order with web image search removed. Relevance judge: for each beat the adapter fetches ≤ 6 candidate thumbnails; one vision call (default Haiku 4.5, model swappable by config `RELEVANCE_JUDGE_MODEL` without code, e.g. → Sonnet if accepted images rate weak on the contact sheet) receives query, subject kind, brief topic line and the thumbnails, returns per candidate a 0–3 score + reasons from a fixed list {wrong_subject, watermark, text_heavy, meme, too_small, nsfw, logo_only}; best ≥ 2 wins, ties by source order; all < 2 → next source → 4.4 ladder. The judge is a cheap FILTER, not the quality bar — the branch-10 vision critic is the real quality gate above it. Code-only hard rejects: short side < 800 px, aspect > 3:1, > 15 MB, non-image body. Rejection is always of a candidate, never of the beat. Budgeted ~₹6/short in 5.5. On record for the `card` kind (tier 2 if needed): the news-card composite pattern (Startuppedia style) — two web-sourced portraits side by side in one card for a two-entity beat, circular logo badge overlapping a corner, title strip with highlighted key words; this re-dress is what makes raw web portraits look professional. Documented in `docs/reference/README.md`.
5.3 — Aspect handling is decided by the renderer from the asset's real dimensions, never by the planner. Portrait and ≥ 1080 px wide after ≤ 1.5x upscale → full-bleed `photo` with Ken Burns (the only case `photo` is allowed). Everything else (landscape, square, too small) → `card` at native aspect, width min(980, 650 × aspect), blurred darkened copy of the same image as the cover behind, Ken Burns on the card not the cover. Planner asked `photo` but asset does not qualify → silent downgrade to `card`, beat records `treatment_downgraded: true` for the contact sheet, no validation error. Generated images are always requested at 9:16 (1080x1920 or nearest) so they qualify for full bleed. Never stretch, never flat-black letterbox, never upscale beyond 1.5x.
5.4 — Rights log = `out/rights.json`, a list with one row per unique asset, written by the asset step, appended by the renderer for music/SFX: `{ id, beat_ids[], kind: image|clip_frame|music|sfx, origin: owner_supplied|web|commons|openverse|pexels|pixabay|generated|library, source_url, page_url, licence: string|"unknown"|"owner", author|null, generated: {model, prompt, render: illustration|photoreal, depicts: named_entity|scene}|null, judge: {model, score, reasons}|null, file, sha256, width, height, fetched_at }`. Two derived files generated by code, never hand-edited: `out/credits.md` (one line per non-owner, non-generated asset "Photo: <author or domain> via <page_url>" + music line) appended to the YouTube description in `meta.json`; AI disclosure — if any row has `generated`, the description ends with "Some scenes are AI-generated illustrations". Gate T9 is a completeness check in code, not a licence check: every beat's asset id has a row; every row has `source_url` or origin `owner_supplied|generated`; every generated row has a prompt; any generated row with `depicts: named_entity` and `render: photoreal` fails the gate (enforces 4.2); photoreal on `depicts: scene` passes.
5.5 — Image generation: Gemini via direct REST (no SDK) behind an `ImageGenerator` interface; `IMAGE_GEN=none | gemini`, and the model/endpoint is a config string (`IMAGE_GEN_MODEL`, `IMAGE_GEN_ENDPOINT`) like the judge model, so switching providers is an `.env` change, not code. `FakeImageGenerator` writes a solid-colour 1080x1920 PNG with the prompt burned in as text. `IMAGE_GEN=none` makes ladder rung 2 a no-op. Prompts are built by code from two templates selected by the planner's `depicts`: `scene` → photoreal archive pattern "<style look> photograph, vertical 9:16: <scene>, <mood>, <lighting>, realistic" (photoreal fine for scenes, environments, unnamed people; "no faces clearly visible" only when no person is intended); `named_entity` → "<style illustration look>, vertical 9:16, illustration of <scene>, clearly stylised, not a photograph" with the look from style front matter. Always appended: no text, no watermarks, no logos. Always requested at 9:16. Cap `gen_max_per_short: 8` (~₹30); cap hit skips to rung 3. One retry on API error, then "nothing generated". Prompt + model stored in the rights row (5.4).
5.6 — Cost ledger: `job.json.cost` holds one row per paid call `{step, provider, model, units, inr}`; every adapter reports units, the ledger prices them from an operator-edited `prices.yaml` (Groq per audio minute, Gemini per image, judge and API planner per 1k tokens, paid search per query) — never prices in code. Per-step allowances in explainer front matter under `budget`: ASR uncapped (~₹0.5), judge `judge_max_calls: 40` (~₹7), generation cap via 5.5 (~₹30), web search `search_max_queries: 60` (free if scraped, else ~₹0.2/query), planner ₹0 on `claude_code` / ~₹8–15 on `api`; worst case ~₹45 on `claude_code`, ~₹55–60 on `api`. AMENDED by 11.3: caps never trade quality. `BUDGET_INR_PER_JOB` (soft, placeholder 50) only flags the job as over-soft-cap on the contact sheet and page; nothing is skipped or degraded for cost — not generation, not the judge, not the critic, not a beat's required visual. `BUDGET_INR_HARD` (placeholder 80) stops the job before the next paid call and marks it `failed` visibly with "budget exceeded at step X" and the ledger shown. The only cost-for-cost trade allowed is one that preserves quality: a relevant searched image ahead of a generated one, which the 5.1 source order already does. Whose subscription and the `api` shared-deployment rule → branch 11. Caching is per job only: `work/assets/` keyed by sha256(query + source) so plan retries and re-renders never re-fetch or re-generate; judge verdicts cached by candidate URL; no cross-job cache in v1.
6.1 — Word sync comes only from the ASR word list after the transcriber fixes (tail re-run, head-smear check, overlap clamp, fix map); the planner never touches word times. Paging is deterministic code from front matter `words_per_page: [2, 4]` (explainer): never split a planner-marked name/number run, break on ASR segment punctuation, break where the inter-word gap > 0.35 s, else fill to max preferring 3. Page timing per research §4: appear at first-word start − 0.04 s, end at min(last-word end + 0.9 s, next page start), last page holds 1.2 s; captions hidden from the finale word onward. Emphasis: planner returns `keywords: [word_index]` in priority order under the research rule (names, numbers, hidden-truth nouns/verbs, final question word); code enforces `emphasis_max_ratio: 0.25` by dropping lowest-priority extras and keeps at most one keyword per page (the first). Language: verbatim in the spoken language, Latin script for English loanwords as ASR returns them, trailing punctuation stripped; planner-cut mis-spoken spans are removed from both audio and words before paging.
6.2 — Explainer `captions` front matter carries the reference typography: Poppins (weights 500–900 bundled under `assets/fonts/`), 74 px, weight 800, line height 1.35, letter spacing 0.5 px Latin only, same font/size for Devanagari; unspoken white 86 %, spoken white, active `#FFD60A` scale 1.0→1.08 over 0.10 s, keyword `#111` on `#FFD60A` box padding 14 radius 14; stroke 2 px four-direction + 3 px drop + 18 px glow; page enter scale 0.94→1 over 0.12 s back-eased, opacity 0.06 s. Inter-word gap rule: every word is laid out in a box sized at its 1.08-scaled width with a fixed advance (`word_gap_px: 22`, a guess to check on the phone), so activation never shifts neighbours; page width measured once at scaled size and wrapped before render if it would exceed 960 px. Max two lines; a page needing three lines is a pager bug caught by a unit test.
6.3 — GLOBAL platform safe area: top 250 px, bottom 320 px, right 140 px reserved for YouTube UI; nothing readable (captions, stamps, lower-thirds) may live there, backgrounds may. Each style picks a caption zone in front matter; explainer anchors the block bottom at y 1460, max two lines → y 1260–1460, touching the PIP bottom. PIP/caption collision is impossible by construction and asserted by the loader: `pip.top + pip.diameter <= captions.anchor_y − captions.max_lines × line_height`, a colliding style fails the loader test. B-roll vs captions: cards end above y 1240 (top 200 + height), stamps stay in the top 60 % (above y 1152), lower-thirds sit at y 1150–1240 and are suppressed on beats whose caption page is two lines (decided by the pager before render). The contact sheet draws the safe-area rectangles as thin outlines on one frame per row.
7.1 — OVERRIDE: sound is its own PRD module, `sound_director`, behaving like a human editor (Discovery/Disney/news style), not a fixed hit table. Supersedes the brief's "short bass hits only on reveals" and the explainer forbidden-list entries "chimes, ticks"; the no-sweep ban, loudness gates and caps stay as hard code (7.3). Architecture: (1) the planner outputs a `sound_story` per short — music theme + mood curve with build/drop points + a per-beat cue list with intent labels (e.g. reveal_drop, money, popup_tick, changeover; illustrative, not a fixed list — the planner reads the script and chooses); (2) music and SFX come only from free copyright-free libraries (YouTube Audio Library, Pixabay, Mixkit, Freesound and similar): a tagged local library under `assets/audio/` (beds by theme/mood, SFX by intent, licence text per file) seeded from these sources and growable, plus a search adapter that fetches new matching tracks when the script's theme needs one not yet local — in v1 the runtime adapter is Freesound (has an API, per-file licence) + local; YouTube Audio Library and Mixkit have no API and seed the library by hand, Pixabay's API has no audio; (3) code renders the sound_story with trims, volume envelopes (swell/drop), sidechain ducking under voice, and changeover alignment to the beat boundary — music-volume automation is in v1; (4) taste rules stay hard code: no sweeps/risers (detector on the SFX stem; bed swells live on the music stem and are bounded by 7.3), loudness targets, cue caps; (5) the Dyson v2 mechanical hits (bass on stamps/reveals/headers, drum on money reveal + finale word, thump on card fly-ins, nothing on whip cuts/punch-ins/rings/lower-thirds) are derived by code from plan events as the guaranteed FLOOR so a short is never flat, and the planner's cues layer on top. Every music/SFX file gets a rights row (5.4). The `educational` draft's "soft tick" is now just a planner cue choice under the same caps.
7.2 — Audio library is a text catalogue the planner reasons over, never audio: `assets/audio/catalog.yaml`, one entry per file `{id, kind: bed|sfx, file, source, source_url, licence, author, duration_s, bpm, key, tags: {theme[], mood[], intent[]}, drop_points_s[], loop_ok, energy: 1–5}`; tags hand-written at seed time, duration/bpm/key/energy measured by a script (librosa or ffmpeg). The sound_story's music section is `theme`, `mood_curve`, `bed_query: {theme, mood, energy}`; code selects the bed by tag overlap + energy distance, ties broken by drop-point fit to the first stamp; below a score threshold the Freesound adapter searches with the same tags, the result is measured, scored and added to the library with a rights row. The planner never names a track. Cues: each `intent` label matches SFX by the `intent` tag; an unmatched intent falls back to the nearest Dyson v2 floor hit — never silence, never a random file. Seed by day 14: 12 beds (suspense, money, history, tech, calm, upbeat; two each) and 20 SFX by intent, every file hand-listened by Shubham and passed through the sweep detector before commit, sourced by hand from YouTube Audio Library / Mixkit with licence text beside each file. On record: this is the industry-standard auto-edit architecture (Wisecut, Descript, CapCut auto, Epidemic/Artlist: pre-tagged catalogues, measured BPM/energy, mood-tag matching, ducking in code); if sound quality disappoints, the fix is a richer catalogue, not a redesign.
7.3 — GLOBAL sound numbers. Chain = Dyson v2 graph verbatim (research §5): voice stem mono fold inside the graph, high-pass 80 Hz, compressor −18 dB ratio 2.5, two-pass loudnorm −19 LUFS / −3 dBTP; bed sidechain threshold 0.06 ratio 2 attack 20 release 400; master two-pass loudnorm −14 LUFS / −1.5 dBTP + limiter 0.891; voice/music/SFX stems always written beside the mix. Bed: target −11 dB vs voice RMS while speaking, acceptance −9 to −12 dB on the median, ducking ≤ 4 dB, speech band 250 Hz–4 kHz ≥ 20 dB above the bed, fades 0.6 s in / 1.2 s out. Mood-curve envelope bounds on the music stem: swell ≤ +4 dB above target, drop ≥ −8 dB below, any ramp ≥ 1.5 s; a "drop" is a step down at a beat boundary followed by a changeover cue, never a rise into a hit. Cue caps: `cues_max: 20` per 60 s including floor hits, `cues_per_beat_max: 1`, every cue −2 to −10 dB under voice by intent class, none louder than −2 dB. No-sweep check T6 in code: detector rules R1–R4 (flatness > 0.03 sustained > 0.45 s; crescendo ≥ 200 ms rising ≥ 8 dB in ≤ 3 dB steps; cue > 5 s; attack > 150 ms from −20 dB to peak) run on every SFX file at seed time and on the SFX stem at render time; any hit fails T6 and names the cue. T4: master −14 LUFS ± 0.5, TP ≤ −1.5 dBTP.
8.1 — Planner = two sequential calls on the same adapter. (1) Picture call: input `PlanRequest` (2.3), output `PicturePlan`: `cut` (kept/cut spans, cold-open lift with keep|drop), `beats[]` each `{start, end, mode, reason?, kind, subject_kind, depicts?, query, query_fallback, source_intent, event: {stamp|ring|lower_third|none, text?}, money_reveal?}`, `hook`, `finale`, `keywords[]`, `title`, `description`, `hashtags[]`. (2) Sound call: input = validated + snapped `PicturePlan` + transcript + catalogue tags, output `SoundStory` (7.1): `theme`, `mood_curve[]` of `{t, level}`, `bed_query`, `cues[]` of `{beat_id, intent, at: start|event|end}`. Sound is second because cues need snapped boundaries and landed events that only exist after code validates the picture plan. Both outputs are Pydantic models with `extra="forbid"`; the JSON schema is generated from the models and embedded in the prompt — one source of truth. Plan JSON is engine-agnostic: no Remotion or ffmpeg terms in it.
8.2 — Validator outcomes in three classes. Clamp silently (code fixes without changing intent): beat boundaries snapped to word ends, keywords trimmed to the cap, cues trimmed by dropping planner cues before floor hits, mood curve clipped to +4/−8, hashtags ≤ 5, title ≤ 100 chars; every clamp logged on the plan as `clamps[]` and counted on the contact sheet. Reject with a list, retry once: a beat outside min/max after snapping, a `full` beat without a reason tag, consecutive `full` beats, full fraction > 25 %, a tier-2 kind, < 12 unique assets, a duplicated cold-open span without `keep`, a cue on a non-existent beat; the message lists every violation with beat id + rule and the same call is re-sent with the previous output plus the list appended. Fail the job: the retry still violates, or the JSON fails the Pydantic model twice → status `failed`, violation list in `job.json` and on the page, no render (a plan that cannot pass the grammar twice is a planner/prompt bug to see, not a short to hand-fix). Picture and sound calls each get their own single retry; retries are ledger rows.

9.3 — Infographics are composed in code, never generated as one image (AI garbles borders, cities and labels). Data visuals: `chart` drawn in code from planner `series` + `labels`. 9.4 — GLOBAL transition vocabulary implemented once in the renderer, each style enabling a subset in front matter (`broll.enter_transitions`). Enter: `cut`, `fade` 0.35 s, `whip` 0.22 s with 14 px directional blur, `zoom` 0.3 s from 1.6, `spring` fly-in from off-frame (damping 14, stiffness 160, mass 0.7), `wipe` 0.25 s for map region changes. Exit is always `cut` or `fade`; the next beat's enter carries the motion. Explainer enables cut/fade/whip/zoom/spring with `whip_max_per_3_beats: 1` and never two whips in a row (whip on every cut is the CapCut-template tell). Hitech: cut/fade/wipe/zoom. Educational: cut/fade. Animated: all six. Planner sets `enter: <name>` per beat (default `cut`); validator rejects names outside the style list and enforces whip spacing. No transition ever triggers a cue: the 7.1 floor rule stays, and a planner cue whose `at` coincides with an enter transition is rejected unless the beat also has a landed event.
10.1 — Technical gate = `shortsmith.qa.technical`, one module, runs T1–T13 in order, writes `out/qa.json`; any FAIL stops delivery. T1 codec/container/geometry (ffprobe); T2 frame count = round(dur × 30); T3 duration ≤ 60.000 s, beats contiguous within 0.011 s, finale 0.8–1.2 s; T4 master −14.0 ± 0.5 LUFS, TP ≤ −1.5 dBTP (ebur128); T5 caption pages cover 3 random timestamps + lip-sync lag 0 ± 1 frame by envelope cross-correlation of voice stem vs cut clip; T6 R1–R4 on the SFX stem (7.3); T7 mean luma ≥ 12/255 every frame, no identical-frame run > 0.5 s before the finale (signalstats + framehash); T8 plan validates with zero unresolved violations, render log has no NetworkError; T9 rights log completeness (5.4); T10 mid-word cut: every `cut` boundary within 0.03 s of a word start/end (new, inherit 10); T11 PIP geometry: 3.3 face box fully inside the circle on the 8 strip frames, chin above 90 % of the window; T12 safe area: no caption/stamp/lower-third geometry inside the 6.3 reserved zones (from plan geometry, not pixels); T13 budget: ledger total, per-step caps and over-budget degradations recorded. Revision proofs (a) video-stream md5 and (b) region-confined pixel diff live in the same module as commands, not gates, run only on a revision.
10.2 — Editorial gate is a vision critic that runs on EVERY job from day one, not a human-only rating; a user should not have to check every short. The critic scores frames + the contact sheet against `docs/reference` (Shubham's approved shorts plus top-creator reference frames per category, grown over time) with a rubric (hook, B-roll relevance, mode variation, density, captions, PIP framing, sound, payoff, integrity, embarrassment — the E1–E10 lines, 1–10 each) and writes score + reasons per line onto the contact sheet and into `out/qa.json`. Calibration: ADVISORY while Shubham is the only user — the critic rates, Shubham rates on the phone, both are stored on the job and compared; once the critic matches the phone verdict (pass/fail at the same line) on at least 4 of 5 consecutive shorts it becomes BLOCKING, and that moment is when the system counts as automated. Pass lines: day-14 worth-continuing gate = Shubham's phone rating, ≥ 6/10 on 3 of 5 recordings; critic rubric pass line once blocking = 7/10. Every published short also logs real YouTube performance (views, retention, published URL) on the job so the critic can later be validated against actual audience response. Critic model is a config string like the judge model (5.2).
10.3 — The reference library is a core product asset, bigger than Shubham's two shorts: a mini library of top-performing shorts from top-subscribed channels across categories (history, geopolitics, finance, product, motivation, science, …), and the critic compares against THEM, the market's best. (1) Library builder tool in the repo (`shortsmith.reference add <url|channel> --category <c>`): downloads a local copy (yt-dlp, git-ignored under `work/reference/<category>/` like current media; only analysis is committed), extracts frames with the same ffmpeg command, and auto-analyses the short into measured pattern data — cuts per 10 s (ffmpeg scene-change detection), caption pages per 10 s (OCR on a 4 fps strip), visual-change rate (frame-difference energy), B-roll fraction and presenter mode timeline (face detector: face size → full / PIP / off), hook structure in the first 2 s (frame strip + vision description), transition density, sound-hit density (onset detection on the non-speech band) — written into `docs/reference/<category>/README.md` in the existing format, each figure tagged MEASURED or ESTIMATED as research.md does. (2) The critic rubric anchors on those measured patterns plus the "what it does well" text, so a score means "matches what top shorts measurably do". (3) Shubham's approved and rated shorts stay in the library as the calibration anchor: top-creator entries define the ceiling, Shubham's rated shorts define what a 6 and an 8 mean, so the critic stays calibrated to the phone verdict per 10.2 and is not crushed by MrBeast budgets. (4) Seed ≥ 3 reference shorts per category by day 14 (Shubham supplies URLs, the tool does the rest); growing the library is one command per new short forever. Critic inputs per job: contact sheet at 1 fps, 8-frame PIP strip, hook strip (first 2 s at 4 fps), plan summary text (beat count, mode fractions, density, clamps, rescued beats, asset origins), stem balance report, transcript, plus the job's category pattern data and frames and the approved-shorts anchors; category is set by the planner from a fixed list. Critic output is a Pydantic model: E1–E10 scores with one reason each, overall, up to five "fix in 5 minutes" notes shown on the page. Rating capture: job page shows short, contact sheet, critic scores, a 1–10 slider + note → `job.json.rating`; `data/calibration.json` tracks the critic-vs-phone match streak and the page shows "critic agreed N of last 5".
10.4 — Contact sheet `out/contact.jpg`: row 1 = hook strip, first 2 s at 4 fps; then one frame per second at 270 px wide, six per row, time label each, and under every frame a one-line strip: beat id, mode letter (F/P/O), kind, asset-origin letter (U/W/C/G = user/web/commons/generated), red corner mark if the beat was rescued (4.4), downgraded (5.3) or clamped (8.2); safe-area outlines (6.3) drawn on the first frame of each row; last row = summary panel with T1–T13 green/red dots, critic E1–E10 scores + overall + the five fix notes, ledger total. Under 2 MB. 11.1 — Job statuses in order: `uploaded` → `transcribing` → `planning` → `sourcing` → `rendering` → `qa` → `delivered` → `passed | rejected`, plus `failed` from any step with `error: {step, message, detail}`; every transition writes `job.json` and appends a timestamped line to `job.log`. 11.2 — Passcode: one shared `SHORTSMITH_PASSCODE` entered once on `/`, stored as a signed cookie for 7 days (signing key derived from the passcode, so rotating it invalidates every cookie); every route except `/health` checks it; a wrong passcode gets a 2 s delay and a per-IP counter, 10 failures in 10 min blocks that IP for an hour, in memory. Limits in `.env` with defaults: `MAX_UPLOAD_MB=500`, `MAX_JOBS_PER_DAY=10` (global), `MAX_QUEUE=3` (a fourth submission is refused with "try in an hour"), `MAX_JOB_MINUTES=30` (worker kills the step and marks `failed` at that step). Sweeper: in-process background task every 15 min — deletes `input/` and `work/` for jobs > 24 h from `uploaded`, deletes the whole job directory at 7 days, never touches a running job; each deletion is a `job.log` line and `job.json` records `swept_at`; the same code path is a CLI with `--dry-run`, testable with a fake clock. 11.3 — Cost philosophy: cost reduction is never a reason to compromise quality; if a high-quality short genuinely costs ₹100 or ₹200 that is acceptable — quality bar first, then cost measured honestly. ₹50 is an inherited ESTIMATE from the brief, not authority. (1) The SYSTEM derives the caps: after Shubham's first 10 metered test jobs across varied scripts (image-heavy, presenter-heavy, infographic-heavy), compute the cost distribution of jobs that PASSED the quality bar and propose soft cap ≈ p90 of passing jobs, hard cap above it; `BUDGET_INR_PER_JOB=50` / `BUDGET_INR_HARD=80` are placeholders reviewed at the day-14 gate with ledger data (`shortsmith gate` prints the distribution and the proposed caps). (2) The ladder may only trade cost where quality is preserved (searched image replacing generated is fine); skipping the critic, skipping needed graphics, or starving a beat of its required visual is never allowed — fail visibly instead (5.6 amended). (3) Measurement is a product feature: every job page shows the full per-step cost breakdown, cash INR and subscription tokens side by side, plus a running average cost per passing short. (4) Cash-only counting: only ledger rows with `inr > 0` count toward caps. Subscription accounting counts ONLY tokens Shortsmith jobs themselves consume — never Shubham's other work or the monthly fee; per-short subscription cost = that job's own tokens valued at the api-equivalent rate from `prices.yaml`, shown for comparison. Decision rule, arithmetic reviewed at day 14: if monthly shorts × api-planner cash cost is cheaper than the api-equivalent value of the tokens Shortsmith consumes, or quota pressure hits Shubham's other work, flip `PLANNER=api`. `PLANNER=claude_code` requires `SHORTSMITH_SINGLE_OPERATOR=true` at startup (subscription use is single-operator only); a shared deployment must run `PLANNER=api` with `ANTHROPIC_API_KEY`, enforced as a startup config error. Daily guard `BUDGET_INR_PER_DAY=500` across jobs; when reached the upload form says "daily budget reached" until midnight IST.
