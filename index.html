The two latest jobs on disk

Both ran on 2 October 2026 in strict mode, one after the other, on an 8 GB laptop. Strict mode refuses to deliver a reel that is worse than planned, so both stopped at a technical check. The reels exist; neither was delivered.

Why this is on a portfolio page: a line that stops loudly, names the beat and the cause, and keeps the evidence is worth more to the next engineer than one that quietly ships a worse reel. The 60-second limit and the chin-in-circle rule both came from real failures and are now tests.

The bar that counts is a phone rating

Passing all thirteen checks proves a reel is technically sound. It does not prove anyone would post it. So every delivered reel is rated on a phone: 6 out of 10 means I would upload it after at most five minutes of fixes, 8 means as it is. The rating is stored on the job and the next tickets come from what it exposed.

The gate for continuing is 3 of 5 own recordings at 6 or better. Two have reached it so far, from the same recording. Strict mode was switched on after those runs and has refused the two jobs since.

Engineering

Built to be operated, not just demoed

Adapters and fakes

  • Every external call sits behind an interface with a fake twin: transcriber, planner, judge, image sources, generator, audio search, renderer, critic.
  • The whole line runs end to end in tests with no network and no spend; 2,204 test functions in 106 files.
  • Two planner adapters, one prompt file, one parser: the CLI and the API produce the same plan shape.
  • Pydantic models with extra="forbid" reject any field the model invents.

Reliability

  • A time budget per step; the render budget scales with frame count; a renderer still producing frames is never killed, only a stalled one.
  • Every subprocess goes through one launcher the watchdog can kill: ffmpeg, Remotion, the Claude CLI.
  • Cost caps stop a job before the paid call, never after. Cost never degrades a step.
  • Strict mode: one helper at every downgrade site, no local if-strict branches; every finding goes to a quality log.
  • Retry re-enters exactly where the job failed; a rescue rewinds to the right step and runs on.

Security

  • Keys live only in a local .env, moved out of the repo before any unattended agent run.
  • Agent permissions are an allowlist: no pushes, no installs, no network, no reading .env.
  • HMAC-signed passcode cookie on every route; the app refuses to start without a passcode; per-IP lockout after ten wrong tries.
  • Every model-written string is HTML-escaped; no shell in any subprocess call; upload body size limited on the socket.

Method

How it was built

I wrote the brief and made every product decision. Claude Code agents wrote the code one ticket at a time, tests first, inside a context budget. A second Claude instance reviewed each change against the real files in a fresh context, and my rating of each real reel decided what got built next.

  1. 01Brief and research

    The problem, the quality bar and the lessons of an earlier engine, written down.

  2. 02Grilling

    One question at a time until every branch had a written decision.

  3. 03PRD

    Modules, contracts and what is out of scope.

  4. 04Thin slices

    106 tickets, each one end to end through the line.

  5. 05Agent builds

    A fresh agent per ticket, tests first, a hard token budget, hand-off files.

  6. 06Review and rate

    Fresh-context code review, then a real recording rated on the phone.
